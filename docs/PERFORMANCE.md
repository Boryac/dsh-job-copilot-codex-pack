# 性能与降级实测（T4.4 / A6）

> 本文件由 `scripts/measure_performance.py` 生成，数字来自本机实测，不是估算。
> 全部为 Mock 链路：不调用天眼查付费接口、不调用 LLM、不发真实搜索请求。

## 1. 环境

- 平台：Windows-11-10.0.26300-SP0
- Python：3.13.14
- 样本：`templates/samples/resume-bd.txt` + `jd-bd.txt`，公司 `云栖生活`
- 迭代次数：暖跑 1 次 + 正式 20 次

## 2. basic 路径耗时（毫秒）

| 指标 | 端到端墙钟 | 各步合计（timings.total） |
|---|---|---|
| P50 | 9.0 | 4.0 |
| P90 | 9.3 | 5.0 |
| 最大 | 10.0 | — |
| 最小 | 8.6 | — |

分步 P50 / P90：

| 步骤 | P50 | P90 | 预算（02 第 4 节） |
|---|---|---|---|
| 简历结构化 | 1.0 | 1.0 | 30s |
| JD 拆解 | 0.0 | 0.0 | 20s |
| 公司背调 | 1.0 | 1.0 | 30s |
| 四维匹配 | 1.0 | 1.0 | 计入端到端 |
| 内容生成 | 1.0 | 2.0 | 分段 |

结论：端到端 P90 = 9 ms，远低于 02 第 4 节要求的 120000 ms 上限。
但必须说明：Mock 模式没有网络往返与 LLM 推理，这里的数字只证明**编排与校验本身不是瓶颈**，不能当成 live 模式的耗时承诺。live 耗时需接入真实 key 后按同一脚本重测，已列入 PROGRESS 的「v2 Phase 0 待验证项」。

| JD 拆解预算耗尽 | ok | 3 | 按设计快速失败（TIMEOUT，fallback=pasted_text_required）：没有 JD 就没有可分析的基准，不输出半成品 |

## 4. 口径说明

- 超时用 `MOCK_FORCE_TIMEOUT=resume|jd|company|generate` 注入，注入点在 `_run_with_budget` 内，与真实预算耗尽走同一异常路径，因此降级分支是真被执行过的，不是纸面承诺。
- 「JD 拆解超时」故意设计成**快速失败**而不是降级出半成品：没有 JD 就没有可对比的基准，输出一份没有岗位信息的报告只会误导用户。
- 「简历超时」与「公司超时」都继续出报告，并在报告与摘要卡片上写明降级原因。
- 「deep 预估后取消」验证的是零付费：预估卡片不计费，幂等键相同，重复预估不会产生调用。
