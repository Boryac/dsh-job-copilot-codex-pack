# 性能与降级实测（T4.4 / A6）

> **口径（2026-11-05 修订，必读）**：本文件全部数字来自 **Mock 链路**——
> 不调用天眼查付费接口、不调用真实 LLM、不发真实搜索请求，网络往返为 0。
> 因此 **9 ms 这个数字不能作为 live 耗时结论**，只能证明"编排 + 校验 + 报告拼装本身不是瓶颈"。
> live 时延目前**未实证**，原因见第 5 节（不只是缺 key，还有一处结构性阻塞）。

- 平台：Windows-11-10.0.26300-SP0

## 4. 口径说明

- 超时用 `MOCK_FORCE_TIMEOUT=resume|jd|company|generate` 注入，注入点在 `_run_with_budget` 内，与真实预算耗尽走同一异常路径，因此降级分支是真被执行过的，不是纸面承诺。
  **但注入发生在 Mock provider 内部**：它证明"超时会被正确捕获并降级"，不证明"真实网络超时的量级"。
- 「JD 拆解超时」故意设计成**快速失败**而不是降级出半成品：没有 JD 就没有可对比的基准，输出一份没有岗位信息的报告只会误导用户。
- 「简历超时」与「公司超时」都继续出报告，并在报告与摘要卡片上写明降级原因。
- 「deep 预估后取消」验证的是零付费：预估卡片不计费，幂等键相同，重复预估不会产生调用。

## 5. live 时延为什么现在是「未实证」（两个独立原因）

1. **缺密钥**：本机没有 `LLM_API_KEY` / `SEARCH_API_KEY`，live 分支进不去。
2. **结构性阻塞（更关键）**：`app/recon/providers.py::SearchProvider._live_search` 目前**直接抛
   `ToolError(UPSTREAM_ERROR)`**——搜索 API 的请求/响应契约从未核验，代码选择显式失败而不是猜接口。
   也就是说：**即使塞进真实 key，live 搜索仍然跑不通**，"真实搜索 + 真实 LLM 重测 P50/P90"
   不是"补个 key 就能测"，而是必须先定搜索供应商并核验契约。

因此本项在 `docs/PROOF.md` 记为**未实证**，并在 PROGRESS 的 v2 Phase 0 里保留为待验证项，
同时把"搜索契约未核验"单列为前置依赖，避免下次误以为是密钥问题。
